# Roadmap

Build one phase at a time. Each phase: inspect → plan → implement → build → test →
review → report. Do not start a phase while the previous one has a critical
failure. The end goal is a free, public Play Store app that many independent
users can trust with their financial data — that bar is only met at the end of
Phase 8, not before.

## Decisions (locked) — see `docs/adr/` for the reasoning

| Decision | Choice |
| --- | --- |
| Mobile | Flutter (single codebase, Play Store + iOS later), Riverpod state, go_router, Material 3 |
| Backend | Go, stdlib `net/http` (1.22+ method/path routing), no heavy framework |
| Database | PostgreSQL, plain SQL migrations (a small dependency-free custom runner, not `golang-migrate` — see `docs/adr/0001-architecture.md`), `pgx` driver — no ORM |
| Ownership model | Every ledger row carries `workspace_id` (Phase 9; originally `user_id` directly, Phases 1–8); every query is scoped to a workspace the authenticated user is a verified member of — proven by test (cross-workspace isolation), same discipline as the trading platforms' tenant isolation |
| Auth | Email + password, JWT bearer (access + refresh), same pattern proven in the trading platforms |
| AI receipt scanning | An OpenAI-compatible vision model turns a photo into a structured **draft** transaction; the user must review and confirm — the AI never posts on its own. Originally planned as the Claude API; live-testing moved this to Google Gemini (`gemini-flash-latest`) after an intermediate choice (Biznet Gio) was confirmed unable to process images at all — see `docs/adr/0002-ai-receipt-scanning.md` |
| Monetization | Free at launch; no ads/paywall built yet — a deliberate decision, revisit only if asked |

| **9. Workspaces & email** | Move ledger ownership from a user directly to a **workspace** (family/UMKM sharing), with `owner`/`member` roles and email invites; SMTP email sending (`internal/mail`); self-service account deletion now cleans up a solely-owned workspace instead of relying on a direct FK cascade from `users`. | ✅ **live-verified working** (2026-09-13): `go build`/`go vet`/`go test` all clean (114 Go tests), then the full flow run against a real Postgres in Docker end to end via curl — register (personal workspace auto-created, 6 default categories seeded into it) → create a second, shared workspace → invite by email (`NoopMailer` logs the invite link, since no real SMTP password is configured — fixed mid-verification to actually log the link/body, not just to/subject, or a self-hosted no-SMTP deployment would have no way to retrieve it at all) → accept → the invited member sees the inviting owner's account in the shared workspace, and vice versa → a member attempting to invite/remove gets 403, a non-member fetching another workspace's data gets 404 → deleting the owner's account (`DELETE /auth/me`) succeeds and, confirmed via `psql`, deletes their solely-owned personal workspace entirely while the shared workspace and the remaining member's access to it stay fully intact. This surfaced and fixed a real bug live: migration `0005`'s new `created_by_user_id`/`invited_by` columns initially referenced `users(id)` with no `ON DELETE` action (Postgres default `RESTRICT`), which would have made `DELETE /auth/me` fail with a foreign-key violation for any user who ever created a ledger row — i.e. always, since categories are auto-seeded at registration. Passkeys/WebAuthn, a dashboard screen, and the "modern card" UI pass from the same original request are not started. |

## Definition of Done (v1 public release)

Builds clean (Go: `go build`/`go vet`/`go test`, enforced by CI on every push;
Flutter: `flutter analyze`/`flutter test`, also in CI — not yet actually
green anywhere, since this has never run against a real Flutter SDK) · per-user
data isolation proven by test · auth is solid (hashed passwords, short-lived
access tokens, revocable refresh tokens) · a user can add an account, log income/expense
manually or by photographing a receipt (reviewing the AI's draft first), and see a
monthly report · a user can delete their own account and data from within the app ·
backups exist and a restore has actually been tested · secrets are never committed ·
privacy policy legally reviewed and published · a human has reviewed and approved the
Play Store listing and pressed publish.
